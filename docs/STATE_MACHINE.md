# 状态机结构（含各转移的实测耗时）

来源：`runner_states.py`（状态与 Ctx）、`runner_states_impl.py`（各状态实现）、
`auto_course.py`（`run()` 主循环、各动作函数）。时间标注分两列：**典型**来自 2026-10-10/11
这次实跑的日志时间戳，**最坏**来自代码里的 sleep/重试上限。

## 一、结构

```
                         ┌──────────────────────────────────────────┐
                         │ INIT                                     │
                         │ 版面校准 + 定位当前小节                   │
                         │ 典型 1~4s / 最坏 ~30s                    │
                         └───────────────┬──────────────────────────┘
                                         │ 总是
                                         ▼
        ┌────────────────────────────────────────────────────────────────┐
        │ OBSERVE   读一次页面（截图+OCR+像素测量）                        │
        │ 典型 2~4s（页面被滚走时要 +4s：发 Home 重读）                    │
        └───┬───────────────────┬────────────────────┬───────────────────┘
            │ 有题              │ 任务点已完成        │ 其余
            │ (quiz, ≥2 选项)   │ (done)             │
            ▼                   ▼                    ▼
    ┌───────────────┐   ┌───────────────┐   ┌──────────────────────────┐
    │ QUIZ          │   │ ADVANCE       │   │ PLAY                     │
    │ 模型选答案+提交│   │ 找下一节+确认  │   │ 保证在播                  │
    │ 典型 5~8s      │   │ 典型 4s        │   │ 典型 5s + 15s poll ≈ 20s │
    │ 最坏 4 次重试  │   │ 最坏 ~2.5min   │   │ 最坏 ~45s + 15s          │
    └───────┬───────┘   └───────┬───────┘   └────────┬─────────────────┘
            │ 总是               │ 成功/结束            │ 见下三支
            ▼                    │                     │
    ┌───────────────┐            │        ┌────────────┴─────────────┐
    │ VERIFY        │            │        │ 已在播 → OBSERVE          │
    │ 判对/错/未知   │            │        │ 启动了 → OBSERVE          │
    │ 典型 2~3s      │            │        │ 拿不到前台 → OBSERVE(+5s) │
    └───┬───┬───┬───┘            │        │ 点不动/无解 → STUCK       │
        │   │   │                │        └──────────────────────────┘
 correct│   │wrong  │unknown     │
        │   │       └────────────┘（回 OBSERVE 重读）
        │   └──► QUIZ（排除刚被拒的选项）
        ▼
    ADVANCE ──► OBSERVE

    ADVANCE ──► DONE   （目录里没有比游标更大的编号 → 全课结束，写 stopped=done）
    ADVANCE ──► STUCK  （读到 ≥3 行但仍找不到下一节 → 求助）
    OBSERVE ──► STUCK  （抓不到课程页）
    QUIZ    ──► STUCK  （模型给不出答案 / 选项不在屏上 / 提交按钮不可注入）
    PLAY    ──► STUCK  （UIPI 丢点击 或 点满 3 次仍不动）

    STUCK ──► OBSERVE  （收到求助回复，比如 click/answer/skip）
    STUCK ──► ABORT    （收到 abort 或 stop 标志）
```

## 二、每个状态的动作与耗时

| 状态 | 进入时做什么 | 典型 | 最坏 | 出口条件 |
|---|---|---|---|---|
| INIT | **刷新页面（Ctrl+R，+9s）**；`autocalibrate()`（有缓存≈0s；无 player 时重测 3 次）；`infer_cursor_from_chapter()` | 10~13s | ~40s | 无条件 → OBSERVE |
| OBSERVE | `capture_page()`：聚焦 0.5s + 截图 + 全屏 OCR(1.5~3.5s)，校验页面标记，最多 6 次；`detect_quiz`；`taskpoint_done`；`quiz_option_rows`；`quiz_question_text`。若「有提交无题型横幅」→ 发 Home + 重读（+4s） | 2~4s | ~30s（→ CaptureError → STUCK） | 有题→QUIZ；已完成→ADVANCE；其余→PLAY |
| PLAY | `ensure_playing()`：采样 A → 2.5s → B → 运动比较；静止则再 2.5s + C；量播放器方框；**先看标签喇叭**（`audio_playing()`，0.3s）；喇叭说没在播（或有播放按钮/时间码）→ **点视频正中央**（`play_click_target()`，量不到方框就用屏幕中心）；都判不出来 → 时钟探针（悬停底部条 + 两次读码 ≈ 18~22s，注意**不是**控制条里的按钮坐标）；点击前 UIPI 预检 + 聚焦；每次点击后 2.5s + 采样比较 | 5s（在播）<br>+15s poll | ~45s + 15s | 在播/启动成功→OBSERVE(+15s)；拿不到前台→OBSERVE(+5s，不计尝试)；点满 3 次或 UIPI→STUCK |
| QUIZ | `choose_answer`（缓存≈0s；否则 API 1~3s；被拒选项再问一次）；点选项 + 1.2s；点提交 + 2.5s | 5~8s | 4 次尝试 | 总是→VERIFY；无答案→STUCK |
| VERIFY | 聚焦 + 0.6s + `capture_page` + 颜色判定 | 2~3s | ~8s | correct→**OBSERVE**（并写缓存，避免中途题目把后半段视频跳过）；wrong→QUIZ；unknown→OBSERVE |
| ADVANCE | 若任务点已完成且本小节还没刷过 → **刷新（+9s）**并重读；目录行 <2 时再重读；`resolve_next`：可见行命中≈0s，否则 `ensure_row_in_catalog`（**刷新**重读，最多 3 次）→ `scroll_catalog_for_next`（同样刷新，最多 3 次）；`advance_to`：读 chapterId（12s）+ `verified_click`（+3.0s）+ 再读 chapterId（25s） | 12~20s | ~1.5min | 成功→OBSERVE；游标 == **20.5**→DONE；否则→STUCK（读不全不去猜"课程结束"） |
| STUCK | `save_state(stopped=…)` + 写 `auto_help/request.json` + `waiting` 标志，阻塞等回复（每 3s 轮询，每 120s 一行日志） | 0s~ | `help_timeout=1800s` | 有回复→OBSERVE；abort/stop→ABORT |
| DONE | 写 `stopped="done"`，退出码 0；监督器据此停止重启 | 0s | 0s | 终止 |
| ABORT | 退出码 9 | 0s | 0s | 终止 |

## 三、定时器与上限（默认值）

| 参数 | 值 | 作用 |
|---|---|---|
| `--poll` | 15s | PLAY 在播时每轮睡眠（`min(poll,20)`）；也是"发现题目/播完"的最大间隔之一 |
| `--stuck-after` | 1500s（25min） | 游标长时间不前进 → 强制 STUCK，理由写明状态与游标 |
| `--help-timeout` | 1800s（30min） | STUCK 等回复的上限 |
| `--max-cycles` | 60 | 步数预算 = `max_cycles × 40` = 2400 步 |
| `max_play_attempts` | 3 | PLAY 连续失败几次后求助 |
| `max_quiz_attempts` | 4 | 同一题最多答几次 |
| `read_chapter_id_stable` | 12s / 25s | 跳转前 / 跳转后的 chapterId 重试窗口（每 2.5s 一次） |
| `ensure_row_in_catalog` | 12 次 ×(读+0.8s) | 按编号找行 |
| `scroll_catalog_for_next` | 10 次 ×(读+0.8s) | 按顺序找下一行（跨章用） |
| `ensure_playing(max_tries)` | 4 | 单轮内最多点几次播放 |
| `video_is_advancing(wait)` | 10~12s | 时钟探针两次采样间隔 |
| 监督器 `--stall` | 420s | 日志 7 分钟没动静就杀 runner 重启（求助等待期间不杀） |
| 监督器轮询 | 20s | 检查 runner 存活 / 日志新鲜度 |
| 监督器 `--max-restarts` | 40 | 重启上限；`stopped=done` 或 `stuck: …` 时不再重启 |

## 四、由此推出的"察觉延迟"（这是状态机的时间语义）

| 事件 | 最快 | 典型 | 最坏 |
|---|---|---|---|
| 视频播完被察觉 | ~1 轮 | ~21s | ~35s（含时钟探针时） |
| 题目弹出被察觉 | ~1 轮 | ~21s | ~35s |
| 视频被暂停（失焦/误点）被察觉 | ~1 轮 | ~21s（画面在动时靠运动检测） | ~40s（静止时靠时钟探针） |
| 恢复播放 | 察觉后 1 次点击 | +5s | +45s（点满 4 次） |
| 跳转完成被察觉 | 4s | 10~30s | ~2.5min（目录要滚动查找时） |
| 真卡住时的求助 | — | — | 1500s（25min）后才报，除非状态自己判定失败（PLAY 3 次 / QUIZ 4 次 / 目录读不到） |

## 五、已知的薄弱点（不是状态，别误读）

* **"暂停"不是一个状态**：它是 PLAY 里的一个分支（喇叭说没在播 → 点视频中央）。
* **点击一律落在视频正中央**（操作者要求）：不瞄准播放按钮。这个播放器点视频本体就是
  播放/暂停切换，而平台的大播放按钮正好画在视频中心，所以中央既是按钮又是最宽容的目标。
* **页面的滚动已彻底移除**：以前 `ensure_row_in_catalog`/`scroll_catalog_for_next` 会发
  滚轮（最多 36 格），目录滚不动时事件冒泡到整页 —— 操作者看到"视频窗口自己在滚"。
  现在改成**刷新 + 重读**（最多 3 次），滚轮只保留在求助回复的手动动作里。
* **课程终点是常量** `LAST_SECTION = "20.5"`：目录不能回答"是否结束"（曾在 8.2 误判结束，
  实际还有 8.3，刷新后又露出 9.x）。读不到下一行 = 目录读不全 → STUCK，不是 DONE。
* **状态机不验证"观看时长在增长"**：现在有标签喇叭（直接信号）+ 时钟探针兜底，但平台的
  进度指示仍未读取。
* **拿不到前台就不点**：有意为之（防误点别的窗口），代价是操作者用电脑期间视频会停住。
* **日志不记录"谁"**：只记录事件（start/stuck/done/refresh），不记录哪个进程或哪个人触发。
